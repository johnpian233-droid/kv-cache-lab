# kv-cache-lab

[English](README.md) | **中文**

## 简介

`kv-cache-lab` 是一个单脚本实验台，只用算术、不用营销，回答一个问题：
**在消费级显卡上，KV cache 量化到底省多少显存？**

厂商说"省一半"。在 8 GB 笔记本显卡上，实测是 **KV cache 省 40.6%、32K 上下文的总显存
省 19.6%**。差额来自一笔量化打折不了的固定开销——约 **4.1 KiB/token**。
仓库里有产出这些数字的脚本、脚本跑出的原始 CSV、以及拟合的推导，每个结论都可以自己复算。

不依赖任何框架，零第三方库。一个脚本、两份 CSV、一本账。

## 性能

实测环境：RTX 4060 Laptop（8188 MiB）、Qwen2.5-1.5B（Q4_K_M）、Ollama 0.40.6、
`OLLAMA_NUM_PARALLEL=1`。每个点对应一次模型加载；数值是「完全卸载后的空闲显存」与
「按该长度加载后的显存」之差。

### 实测斜率

| KV 类型 | 实测斜率 | 理论斜率 | 实测/理论 | 截距 | R² |
|---|---|---|---|---|---|
| **f16**（基准） | **32.11 ± 1.24 KiB/token** | 28.00 | 1.15× | 1119 ± 20 MiB | 0.9956 |
| **q8_0** | **19.08 ± 1.05 KiB/token** | 14.88 | 1.28× | 1118 ± 17 MiB | 0.9910 |

**斜率 = 这台机器上每 token 的真实成本。截距 = 模型的固定重量**（权重 + CUDA 开销），
它永远不打折。

两次独立测量相隔一小时、桌面占用不同，拟合出的截距**只差 1 MiB**。这是这套方法可信的证据。

### 过路费：实测比理论多出来的那部分

| | 纯 KV 理论 | 实测斜率 | 差额 |
|---|---|---|---|
| f16 | 28.00 | 32.11 | **+4.11** |
| q8_0 | 14.88 | 19.08 | **+4.20** |

两种精度下的两个差额几乎一模一样——说明它不是量化造成的，而是一笔固定成本：

- **约 1.0 KiB/token** — attention mask 缓冲（开不开 FlashAttention 都要建）
- **约 1.0 KiB/token** — 量化 K/V 在计算时临时还原成 f16 的副本
- **约 2.0 KiB/token** — 分配器碎片与对齐

这笔过路费不随精度变化，所以量化永远到不了理论比例。
**省的部分随上下文涨，过路费不涨。**

### 对你的账单意味着什么

| 问法 | 答案 |
|---|---|
| "q8_0 让 KV cache 本身省多少？" | **40.6%** |
| "32K 上下文下，总显存省多少？" | **19.6%** |
| "128K 上下文下呢？" | **31.9%** |

"省一半"和"省两成"都对，它们回答的不是同一个问题。**要报价，用后一个数。**

在 32K 处对模型做一次校验——拟合值 vs `num_ctx=32768` 的原始实测值：

| | 按拟合算 | 原始实测 | 差 |
|---|---|---|---|
| f16 | 1119 + 32.11 × 32 = **2146.6 MiB** | 2132 MiB | 14.6 |
| q8_0 | 1118 + 19.08 × 32 = **1728.4 MiB** | 1714 MiB | 14.4 |
| 省下 | **418.2 MiB** | **418.0 MiB** | — |

418 / 2132 = **19.6%**。两条路算出来的节省量完全一样，这才是重点：
**这条线是机器的模型，不是把数据重画一遍。**

### 这个数有多准

五个点、三个自由度、95% Student-t：

| KV 类型 | 斜率 ± 1 SE | 95% 置信区间 | 理论值 | 理论值与区间的关系 |
|---|---|---|---|---|
| f16 | 32.11 ± 1.24 | [28.18, 36.05] | 28.00 | 在区间外，差 0.18 |
| q8_0 | 19.08 ± 1.05 | [15.74, 22.43] | 14.88 | 在区间外，差 0.86 |

两个理论值都落在区间外，所以"过路费"在名义上是显著的。
**但看 f16 的余量：0.18 KiB/token，0.6%。** 再加一个点，就可能把理论值包回区间里，
让"存在过路费"变成"没有可测差异"。

所以上面那节「过路费」，靠的不是这个置信区间，而是**复现**：
两轮独立测量、两种精度、同样的 +4.11 / +4.20 差额、截距只差 1 MiB。
一个系统偏差能穿过多重独立检验，就不是回归噪声。

想要更窄的区间，补测 6144 和 24576 两个点——区间是被 4096→8192 那个台阶撑宽的。

### 原始数据

```
num_ctx   f16 (Δ MiB)   q8_0 (Δ MiB)
  2048        1166          1139
  4096        1224          1177
  8192        1412          1297
 16384        1652          1445
 32768        2132          1714
```

4096→8192 这一段是两条曲线唯一抬头的地方（q8_0 从 19 跳到 30，f16 从 29 跳到 47）。
两次独立测量都在同一位置出现，所以它是系统性的，不是噪声。最可能的原因：某个
FlashAttention 内核在 `n_kv ≥ 4096` 且 `gqa_ratio > 4` 时启用，而 Qwen2.5-1.5B 刚好是 6。
*（机制为推测，未在源码中确认。）*

### 第三档：算出来的，不是测出来的

| KV 类型 | 斜率 | Qwen2.5-1.5B 的 32K 总显存 |
|---|---|---|
| f16（实测） | 32.11 KiB/token | 2146.6 MiB |
| q8_0（实测） | 19.08 | 1728.4 MiB |
| **q4_0（预测）** | **≈ 12.0** | **≈ 1503 MiB** |

q4_0 理论值 7.88 KiB/token，加上同一笔约 4.1 的过路费，落到 12.0——32K 下比 f16 省 30%。
**这一行是算术，不是测量。** 放进表里是为了让你能验证这个模型，而不是相信它：
跑一遍 `--kv-bytes 0.5625`，看它站不站得住。

### 外推到其他模型

KV 成本 = `2 × 层数 × KV头数 × head_dim × 字节数`，所以可以按公式推：

| 模型 | KV/token (f16) | 32K | 128K |
|---|---|---|---|
| Qwen2.5-1.5B | 28 KiB | 896 MiB | 3.5 GiB |
| Llama-3-8B | 128 KiB | 4 GiB | **16 GiB** |
| Qwen2.5-72B | 320 KiB | 10 GiB | **40 GiB** |

一个 72B 模型光"记住聊天记录"就要 40 GB，比它自己的权重还大。
这一行数字，就是 2026 年下半年所有新模型都在做的同一件事。

在你自己的卡上跑一遍脚本，你就有了自己的斜率，剩下的可以自己算。

## 安装

脚本是自包含的，"安装"等于 clone 下来再 pull 一个模型。

```bash
git clone https://github.com/johnpian233-droid/kv-cache-lab.git
cd kv-cache-lab

# 可选：用仓库里的 CSV 复核算术（不需要显卡）
python tests/test_fit.py

# 没有模型就先拉一个
ollama pull qwen2.5:1.5b
```

## 用法

### 测一组配置

```bash
# q8_0 的 KV cache
python scripts/ollama_probe.py --tag q8_0 --kv-bytes 1.0625

# f16 基准
python scripts/ollama_probe.py --tag f16  --kv-bytes 2
```

输出：逐 `num_ctx` 的表、带 1 SE 与 95% 置信区间的最小二乘拟合、外推表，
以及 `ollama_probe_<tag>.csv`。

常用参数：

| 参数 | 含义 |
|---|---|
| `--kv-bytes` | 每元素字节数：f16=2、q8_0=1.0625、q4_0=0.5625 |
| `--seqs` | 要测的上下文长度（默认 `2048 4096 8192 16384 32768`） |
| `--layers --kv-heads --head-dim` | 模型结构参数，用于理论值那一列 |
| `--settle` | 判定"模型已完全卸载"的显存容差（MiB） |

### 切换真正的 KV 类型

设环境变量**并重启服务**——这个设置只在加载时读取。

```bash
export OLLAMA_FLASH_ATTENTION=1          # V 量化强制要求
export OLLAMA_KV_CACHE_TYPE=q8_0         # 或 f16 / q4_0
ollama serve
```

> Windows：用 `set`（只影响当前窗口，立即生效），不要用 `setx`（只对之后新开的窗口生效）。
> 改完必须重启 `ollama serve`，否则不生效。

### 测量方法

每个 `num_ctx`：卸载模型 → 记空闲显存 → 按该长度加载 → 记加载后显存 → 取差值。

**永远比差值，不比绝对值。** 本仓库两轮测量之间，桌面占用差了 419 MiB，差值把这点完全吸收了。

### CSV 字段

| 列 | 含义 |
|---|---|
| `num_ctx` | 请求的上下文长度 |
| `loaded_mib` | 加载后的绝对显存（仅用于排查） |
| `delta_mib` | **测量值** —— 加载后减空闲 |
| `theory_kv_mib` | 同一行按教科书公式算出的纯 KV |
| `load_sec` | 加载耗时 |
| `model`、`ollama_version`、`kv_cache_type`、`kv_bytes_per_elem` | 出处信息 |

`delta_mib` 里含权重。这是故意的：拟合的截距会把权重吸收掉，权重就是靠这一手
才跟每 token 成本分开的。

## 这个仓库不是什么

- **不是 benchmark。** 没有 tokens/s、没有延迟、没有质量评测，只有显存。
- **一台机器、一个模型。** 每组配置五个点。方法通用，数字不通用。
- **不是"q8_0 无损"的证据。** 业界共识是近似无损，但本仓库没验证。别拿它当证据。
- **置信区间很宽。** 自由度只有 3。要更紧的数字，就多测几个点——脚本会诚实报出区间。

## 参与

显卡不同、模型不同、答案当然不同。**开个 issue 报上你的数字**，用「Report a
measurement」模板，带上：

- 显卡与显存：`nvidia-smi --query-gpu=name,memory.total --format=csv`
- 模型 tag + 量化方式、Ollama 版本、`OLLAMA_KV_CACHE_TYPE`
- 脚本跑出来的 CSV

社区测量会汇总成一张表，标上卡型号和斜率。**方法才是重点，数字本来就该不一样。**
