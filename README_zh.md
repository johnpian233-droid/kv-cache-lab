## 简介

`kv-cache-lab` 是一个单脚本实验台，只用算术、不用营销，回答一个问题：
**在消费级显卡上，KV cache 量化到底省多少显存？**

厂商说"省一半"。在 8 GB 笔记本显卡上，实测是 **32K 上下文总显存省 19.5–20.8%**。
另外，在**另一个分母**下，**KV cache 本身省 42–45%**。差额是量化打折不掉的开销：
约 **2.0 KiB/token** 的持续成本（f16），外加 8192 处一次 **约 67 MiB 的分配台阶**。

这两个百分比**不是同一个数的两个部分**。读成"19.6% 其中的 42.3%"会乘出个 8% 来，
那哪个意思都不是。

那个台阶才是真发现，也是大多数 KV 测试做错的地方。单直线拟合给出 32.11 KiB/token，
但数据否掉了这个模型（**F = 2748**，临界值 18.513），支持 **29.99 KiB/token 加 67.1 MiB
台阶**；两者之差在 0.03 KiB/token 内等于台阶除以最大上下文。流传的"固定 4.1 KiB/token
**过路费**"里有一半是这个错误造出来的——本文件里**过路费**一律指*实测斜率减去理论斜率*。

仓库里有产出这些数字的脚本、脚本跑出的原始 CSV、以及两个模型的推导，每个结论都可以
自己复算。

不依赖任何框架，零第三方库。一个脚本、两份 CSV、一本账。

## 性能

实测环境：RTX 4060 Laptop（8188 MiB）、Qwen2.5-1.5B（Q4_K_M）、Ollama 0.40.6、
`OLLAMA_NUM_PARALLEL=1`。每个点对应一次模型加载；数值是「完全卸载后的空闲显存」与
「按该长度加载后的显存」之差。

### 实测斜率

| KV 类型 | 单直线斜率 | 直线+台阶斜率 | 一次性台阶 | 理论斜率 |
|---|---|---|---|---|
| **f16**（基准） | 32.11 ± 1.24 | **29.99** | **+67.1 MiB** | 28.00 |
| **q8_0** | 19.08 ± 1.05 | **17.31** | **+56.2 MiB** | 14.88 |

第一列是"横跨整个网格拉一条线"得到的结果。第二列是把数据真正想要的模型拟合出来之后
的结果。**两者差 6.6% 和 9.3%，下一节说明为什么第二列赢。**

**截距 = 模型的固定重量**（权重 + CUDA 开销），约 1110 MiB。它永远不打折，量化再狠也不动。

### 一条直线藏着一个台阶

五个点、五个单调递增的值。一条直线当然拟合得好：R² = 0.9956。但这个数字**不是线性的
证据**，它是个形式——一条平滑的单调五点序列通常都能给出这个数。R² 回答的是"这条线能不能解释
方差"，不是"这条线是不是对的模型"。

所以要看那条拟合的残差：

```
num_ctx    Δ MiB    相对单直线的残差
   2048     1166        -17.2
   4096     1224        -23.5
   8192     1412        +36.1   ← 一处干净的凸起
  16384     1652        +19.2
  32768     2132        -14.6
```

这些残差不是在乱撒。它们依次是 负、负、正、正、负——一条平滑的弧，峰顶正好落在 8192。
如果直线是真模型，残差的符号应该随机排列。

于是加上那个显然缺掉的项：一次性电平位移。

```
ΔVRAM = b + a · N + c · 1[N ≥ 8192]
```

| | 单直线 | 直线 + 台阶 | F(1,2) | 判决 |
|---|---|---|---|---|
| f16 | SSE 2731.6 | **SSE 2.0** | **2748** | 台阶胜 |
| q8_0 | SSE 1972.9 | **SSE 57.8** | **66.2** | 台阶胜 |

5% 临界值是 18.513，两个统计量都远远超过。f16 的台阶模型残差是 **±1 MiB**——就是
`nvidia-smi` 自己的刻度（它只报整数 MiB）。**一个三参数模型，在五个点上全部落在仪器自己
一格刻度之内**，这就不是对直线的改进了，是**取代**它。

这个 p 值有一点要说明，因为它最容易被漏掉：台阶的**位置**是逐个试出来的——遍历每个内部点、
取 SSE 最小的那个，所以这不是一次干净的单次比较。三个候选位置下，实际的一类错误率更接近
**14%** 而不是 5%。在这里它不改变结论（F = 2748 不是 14% 还是 5% 能左右的数），但如果结果
是临界的，这一条就会决定答案。脚本现在会把这个警告和结论一起打出来。

只拿 8192 及以上的点做拟合，f16 斜率是 **30.000 KiB/token**，三个点在 1 MiB 内共线。
但这个子集**本身就在上面的拟合里面**，所以它不算独立证据。之所以还是把它印出来，是因为
它恰好是曲线做不到的事：三个点落在一条直线上，是台阶留下的痕迹，也是抛物线留不下的痕迹。

### q8_0 那一轮的基线在漂，而这改变了 q8_0 的答案

CSV 里存了 `loaded_mib` 和 `delta_mib`。两者相减，就能把每一行背后那次空闲读数还原出来——
一列从来没人印过的数据：

```
num_ctx    f16 隐含空闲    q8_0 隐含空闲
   2048            1230               811
   4096            1230               805
   8192            1229               805
  16384            1229               789
  32768            1229               785
```

f16 那一轮，基线整张网格只动 **1 MiB**。q8_0 那一轮，动了 **26 MiB**，而且单调下滑。
到底是桌面真的在释放显存，还是读数自己在漂，对下面的结论都不重要：减法把这一整块都塞进了
`delta_mib`，而 26 MiB 是它本该去检验的那个 q8_0 残差（5.8 MiB）的五倍。

所以 q8_0 两种口径都拟一遍——信每一次的空闲读数，或者认为整轮只有一个基线：

| q8_0，基线口径 | 斜率 | 台阶 | SSE | 过路费 |
|---|---|---|---|---|
| 逐点空闲，按记录 | 17.31 | +56.2 MiB | 57.8 | +2.43 |
| 常数基线 = 811 | **16.54** | **+53.2 MiB** | **0.66** | **+1.66** |

两者都站得住，数据里没有任何东西能在它们之间做选择。三个后果，按杀伤力排序：

**f16 那个结论免疫。** 它的基线只动 1 MiB，两种口径都给斜率 29.99、台阶 66–67 MiB、
SSE 2.0、过路费 1.993。这份 README 倚重的是 f16 那一列，而 f16 那一列不在乎这个选择。

**q8_0 的数只能报区间。** 斜率 **16.5–17.3**，台阶 **53–56 MiB**，32K 那个数
**1688–1716 MiB**，过路费 **1.66–2.43**。

**v0.1.2 的一个结论撤回。** 那一版说 f16 过路费 1.99、q8_0 是 2.43，叫它"差 22%"，
并把这点差别当成发现。f16 的 1.99 **落在** q8_0 的区间里面。这个差比一列没记录的数据
带来的不确定度还小，所以**本仓库没有证据说过路费在两种精度下不同。**

还要看误差往哪边偏。用常数基线时，q8_0 的台阶模型 SSE 只有 **0.66**——比 f16 的 2.0 还好，
而且赢二次曲线 **923 倍**。之前读成"q8_0 拟合不紧"的那个东西，是基线在动，不是模型不行。

### 会不会只是条平滑的曲线？

读到这儿你有权怀疑。台阶项是往直线上硬塞的灵活东西，五个点、三个参数，模型有的是空间
自己吊死自己。说不定数据本来就是弯的，"台阶"只是抛物线的马甲。

那就别争，直接把替代模型拟合出来。二次项和台阶模型一样是**三个参数**，两者不嵌套，
所以 SSE 可以直接比，不用罚项：

| 模型 | 参数 | f16 SSE | q8_0 SSE |
|---|---|---|---|
| 单直线 | 2 | 2731.6 | 1972.9 |
| 二次曲线 | 3 | 966.4 | 380.5 |
| 直线 + 台阶 | 3 | **2.0** | **57.8** |

二次曲线把 f16 的 SSE 压到 1/2.8，台阶把它压到 1/1375。拿两个同为三参数的模型对着看，
**台阶赢 486 倍**。

残差说明了原因。二次曲线的残差是 **+2.2、−16.3、+23.8、−11.2、+1.6**——还是那个
负负正正负的摆动，只是幅度小了。抛物线没法只在一个内部点上起一个尖，而不在两头付出代价，
而 8192 正是那个尖的位置。**数据里是个跳变，不是一道弯。**

q8_0 那一列要补两句。第一，它的优势是 **6.6 倍**而不是 486 倍；但如果改用上一节的常数基线
口径，同一个倍数变成 **923 倍**——**一个数量级上的差别，取决于一个数据里根本没法定下来的
选择**。第二，这正是 q8_0 这个对照比 f16 那个更不值钱的原因：f16 那一列在这个选择下不动，
q8_0 那一列会动。

### 台阶为什么重要：它一直被当成每 token 成本在收钱

这个错误值得记一辈子，因为**任何在上下文网格上拉一条直线的 KV 测试都会犯**——包括本文件
更早的草稿。至于具体哪几篇已发表的数字犯了，本仓库没查过，也不声称。

8192 处 67 MiB 的台阶，如果你拒绝建模它，回归就会把它摊到整个区间上。除以最大上下文：

```
67.1 MiB / 32768 token × 1024 = 2.10 KiB/token
```

而这在 0.03 以内就是单直线斜率被抬高的量：32.11 − 29.99 = 2.12。算术闭合了。

再把它和"实测与理论之差"放在一起看。本文件里**过路费**一律指
*实测斜率减去理论斜率*——公式没能预测出来的那部分每 token 成本：

| | 单直线 | 直线 + 台阶 |
|---|---|---|
| f16 相对理论的差额 | +4.11 | **+1.99**（两种基线口径完全一样） |
| q8_0 相对理论的差额 | +4.20 | **+1.66 … +2.43** |
| 两种精度之间的差 | 0.09 | **未能确立** |

那个"固定 4.1 KiB/token 过路费"，**有一半根本不是每 token 成本**。它是一次性的分配台阶，
被拟合按 32K 上下文摊销成了每 token 成本。f16 上真正的每 token 开销是 **1.99 KiB/token**。

下一句本来该写"而且两种精度下不一样"——**这句本仓库撑不住**。q8_0 的区间把 f16 的值包在
里面，也就是说"一个共同的过路费"和"两个不同的过路费"同样符合数据。v0.1.2 说差 0.44，
还说这是单直线 0.09 的"近五倍"。两个数都比一列没记录的数据带来的不确定度小。**这句撤回。**

留下来的东西更窄，但仍然有用：过路费是一个约 2 KiB/token 的数，不是 4.1 KiB/token 的常数；
这两个答案之间的差，就是那个一直被当成每 token 成本在收的台阶。

原来那个论证确实被翻过来了一半。单直线让过路费看起来是常数，并把"一致"当成了机制的证据。
台阶一建模，一致性没了——但本该顶替它的那个机制，证据也没了。所以本文件只报拆解，不报机制。

### 对你的账单意味着什么

| 问法 | 答案 |
|---|---|
| "q8_0 让 KV cache 本身省多少？" | **42–45%**（单直线给的是 40.6%） |
| "32K 上下文下，总显存省多少？" | **19.5–20.8%** |
| "128K 上下文下呢？" | **32.6–34.6%**（外推，无区间） |

"省四成"和"省两成"都对，它们回答的不是同一个问题：前者是 KV cache 对 KV cache，
后者是完整显存账单对完整显存账单。**要报价，用后一个数。**

这些是区间不是点值，原因跟统计无关：q8_0 的基线自己在漂（见上面那节），所以凡是底下压着
q8_0 的比例数，全都继承了这层漂。区间下端是"逐点空闲"口径，上端是"常数基线"口径。
**报其中任何一个数到小数点后一位，都是假精度。**

三个脚注，好让你能复算这些比例。百分比是两条**实测斜率**之比，而每条斜率里都已经含了约
2 KiB/token 的过路费，所以它是"按账单算的 KV 对 KV"，不是"纯 KV 字节"——对纯理论算是
46.9%。这些百分比**不同分母**：32K 那个除以 32K 的拟合值，128K 那个除以一个没有区间的
外推值。而单直线那个 40.6% 是同一种算法，所以第一行至少是同类相比。

有一件事**不在**这些区间覆盖范围内：台阶高度。q8_0 是 53–56 MiB，f16 是 66–67 MiB，
两者的差别这里没有任何解释。

32K 处的校验——两个模型分别对 `num_ctx=32768` 的原始实测值：

| | 单直线 | 差 | 直线 + 台阶 | 差 |
|---|---|---|---|---|
| f16 | 1119 + 32.11 × 32 = 2146.6 MiB | 14.6 | 1105.02 + 29.993 × 32 + 67.10 = **2131.9 MiB** | **0.1** |
| q8_0（逐点空闲） | 1118 + 19.08 × 32 = 1728.4 MiB | 14.4 | 1106.08 + 17.306 × 32 + 56.21 = **1716.1 MiB** | 2.1 |
| q8_0（常数基线） | — | — | **1687.9 MiB** | 26.1 |
| 省下 | 418.2 MiB | — | 415.8 MiB | — |

先说清这是什么：**样本内**。32768 本身就是被拟合的五个点之一，所以这里残差小是拟合质量，
不是预测，而且没有做任何样本外检验。它真正确立的东西更窄，但仍然有用——一个三参数模型
能把五点的数据集复现到仪器的分辨率，而两参数的直线在同一个点上差 14.6 MiB。那 14.6 MiB
正好就是直线拒绝建模的那个台阶。

### 这个数有多准

下面的区间**属于单直线**——五个点、三个自由度、95% Student-t：

| KV 类型 | 斜率 ± 1 SE | 95% 置信区间 | 理论值 | 理论值与区间的关系 |
|---|---|---|---|---|
| f16 | 32.11 ± 1.24 | [28.18, 36.05] | 28.00 | 在区间外，差 0.18 |
| q8_0 | 19.08 ± 1.05 | [15.74, 22.43] | 14.88 | 在区间外，差 0.86 |

f16 的余量只有 **0.18 KiB/token，0.6%**。再加一个点，就可能把理论值包回区间里，
让"存在过路费"变成"没有可测差异"。没人应该把论证架在这么薄的一层上，本仓库也不架。

还要注意这个置信区间**没有回答什么**。它回答的是"假如直线为真，斜率会抖多少"，
不回答"直线是否为真"——后者由 F 检验回答，答案是"否"。留一法（每次丢掉一个点）
证实了这个区间在**抽样噪声**上是诚实的：丢掉任意一个点，单直线斜率在 **31.6 到 35.2**
之间跳，跨度 3.6 KiB/token，约等于 ±2 SE 带的 1.5 倍，而且完全落在报告的 95% 区间内。
区间本身从来不是问题。真正的问题是：抽样噪声在这里根本不是主要误差——**模型选择才是**，
而那个误差是 32.11 对 29.99，比上面这些摆动都大。

台阶模型在主结论上更强，**在精度上更弱**：

- **更强**：F = 2748，临界值 18.513；32K 处**样本内**残差 **0.1 MiB**。
- **更弱**：稳态斜率只有三个点，而这三个点在约 1 MiB 内共线，所以标准误算出来是 **零**。
  那不是精确，那是**无从估计**——三个点估不出自己的散布；而"共线到 1 MiB 内"和"精确共线"
  是同一件事的两种客气程度。

还有第三处不对称，是审稿人最会按着敲的地方：F 检验的分母，就是台阶模型自己的残差。f16 上
这个残差（2.0，也就是每点约 1 MiB）恰好是 `nvidia-smi` 的刻度。所以 F = 2748 是**有条件的**
——条件于"台阶模型的形状是对的"，并且"测量基本无噪声"。这批数据没有纯重复，所以分母分不开
失拟项。**把 F 当成"数据多支持一个台阶"的上界，别当成校准过的 p 值。**

所以诚实的说法是：**f16 的斜率是 30 不是 32，台阶是真的，而两个数都还没有可信的误差棒。**
把每个点重复测几次是能解决这件事的实验。q8_0 那一组事后用另一套协议复现过一次，吻合到
4 MiB（见上面的「独立复现」）——那是一次复现，不是方差估计；f16 那一组一次都没重复过。
它仍然排在「这个仓库不是什么」第一条。

### 独立复现

q8_0 那一组在事后用另一套协议重测了一遍：空闲值连读五次取中位数（原来是单次），加载后连读
九次取峰值，卸载判定改走 `/api/ps`（原来是显存阈值），KV 类型从服务端自己的启动环境里读出来
（原来只是照着参数写）。而且这台桌面**更忙了**——空闲底线上高了 **1078 MiB**。

| num_ctx | 2048 | 4096 | 8192 | 16384 | 32768 |
|---|---|---|---|---|---|
| 第一次（Δ MiB） | 1139 | 1177 | 1297 | 1445 | 1714 |
| 复现（Δ MiB） | 1138 | 1173 | 1301 | 1441 | 1716 |
| 差 | −1 | −4 | +4 | −4 | +2 |

每个点都落在原值 4 MiB 以内，而绝对显存占用已经挪了一整个 GB 以上。直线斜率前一次 19.08、
后一次 19.09 KiB/token；台阶前一次 +67.1 MiB、后一次 +59.8 MiB，位置相同。

这是整个仓库里最强的一份证据，而它证明的是**方法**，不是模型：一个差值吸收了桌面 1078 MiB
的变动和一整套测量协议的改动，回来只差 4 MiB。也正是这一点，让上面那个"q8_0 基线在漂"可以
被叫作局限而不是缺陷——它挪动过的那个数没有跟着挪。

f16 那一组**没有**重测：两轮原始测量之间，服务端的 `OLLAMA_KV_CACHE_TYPE` 被换成了 q8_0，
现在仍是 q8_0，要再测 f16 必须重启 `ollama serve`。它只有内部交叉验证：f16 与 q8_0 两轮在
32768 处的模型占用差 418 MiB，而理论差是 `(28 − 14.875) × 32768 / 1024 = 420 MiB`。这与
"那两轮确实是 f16 和 q8_0"一致，但这是推断，不是复现。

复现过程抓出两个缺陷，都在工具里，不在数据里：

- 卸载判定原本是拿 `nvidia-smi` 比一个绝对阈值。桌面在会话中途涨了 150 MiB 之后，这个阈值
  就永远不可能满足，脚本连报三次"模型可能没卸载干净"，而 `ollama ps` 全程是空的。现在改成
  直接问 Ollama——只有它知道。
- `--kv-bytes` **不配置任何东西，它只是贴标签**。有一轮跑的时候服务端是 q8_0，却传了
  `--kv-bytes 2`，于是被记成 f16，斜率 19.0 KiB/token——是 q8_0 理论的 1.28 倍、f16 理论的
  0.68 倍。它之所以被发现，是因为它和更早那轮 q8_0 吻合到 4 MiB。现在脚本会从服务端启动
  日志里读 `OLLAMA_KV_CACHE_TYPE`，标签对不上就不写 CSV。

### 原始数据

```
num_ctx   f16 (Δ MiB)   q8_0 (Δ MiB)   f16 空闲   q8_0 空闲
  2048        1166          1139        1230         811

  8192        1412          1297        1229         805

```

只要有人想到去减一下。

### 那个台阶到底是什么

三个候选。**一个都没确认，本仓库也不声称知道是哪个。**

- **Attention 内核切换。** Ollama 在某个 `n_kv` 阈值之上会走另一条 attention 路径，
  新路径要分配自己的 workspace。Qwen2.5-1.5B 的 GQA 比例是 6，这类阈值常常就落在那儿。
  一下午能验：用 `OLLAMA_FLASH_ATTENTION=0` 把同一套网格重跑一遍，看台阶是否移动或消失。
- **分配器 arena 增长。** GGML 分配器在 8192 处跨过某个 size class，把整个 KV 缓冲
  向上取整到下一个 arena 边界。
- **模型之外的缓冲。** 这台机器上 Ollama 按显存推出的默认上下文是 **4096**
  （服务日志里 `default_num_ctx=4096`）。某个只在请求超过这个默认值之后才出现的缓冲，
  会正好落在这个位置。

有一条观测能收窄搜索范围：台阶在**两种精度下位置相同**，但**高度不同**
（+67.1 vs +56.2 MiB）。**只看 `num_ctx` 的机制**会这样；**只看 KV 字节数的机制**不会。
数据能说的到此为止。

### 第三档：故意不预测

| KV 类型 | 斜率 | Qwen2.5-1.5B 的 32K 总显存 | 状态 |
|---|---|---|---|
| f16 | 29.99 KiB/token + 67.1 MiB 台阶 | 2132.0 MiB | 实测 |
| q8_0 | 16.5–17.3 + 53–56 MiB 台阶 | 1688–1716 MiB | 实测（基线敏感） |
| q4_0 | 理论 7.88，过路费未知 | — | **不预测** |

这份 README 早一版确实预测过 q4_0：理论 7.88 加上"同一笔 4.1 过路费"得到 12.0。
那笔算术现在不能用了，理由值得说明白。

把台阶建进模型之后，过路费就不是一个干净的数了。f16 是 **1.99**，q8_0 是 **1.66–2.43**——
同一台机器、同一天、同一个脚本测出来的两种精度，一个点值配一个区间。拿一个区间去加理论值，
第三个精度出来的数会带着两位有效数字和零内容。台阶高度更糟：f16 是 66–67，q8_0 是 53–56，
没有任何东西说 q4_0 落在哪儿。

所以诚实的范围只能是：斜率大约 **9.5–10.3 KiB/token**，32K 那个数带着几十 MiB 的
不确定度，这批数据收不窄。**要用 q4_0 的数，就测**：
`py scripts/ollama_probe.py --kv-bytes 0.5625 --tag q4_0`。一条命令，五十秒。

### 外推到其他模型

KV 成本 = `2 × 层数 × KV头数 × head_dim × 字节数`，所以可以按公式推：

| 模型 | KV/token (f16) | 32K | 128K |
|---|---|---|---|
| Qwen2.5-1.5B | 28 KiB | 896 MiB | 3.5 GiB |
| Llama-3-8B | 128 KiB | 4 GiB | **16 GiB** |
| Qwen2.5-72B | 320 KiB | 10 GiB | **40 GiB** |

一个 72B 模型光"记住聊天记录"就要 40 GB，和它自己 4 bit 的权重是一个量级，比 8 bit 的还大。
这一行数字，就是 2026 年下半年所有新模型都在做的同一件事。

注意这张表是什么：**纯理论，没有加过路费**。这台机器上 f16 实测比理论高约 7%，但那 7%
是机器事实，不是定律；台阶高度在测之前更是谁也不知道。把这些数当地板看。

在你自己的卡上跑一遍脚本，你就有了自己的斜率，剩下的可以自己算。

## 相关工作

这是一份小的测量笔记，不是方法论文。它站的东西、以及它故意不碰的东西：

- **llama.cpp / GGML** 是这里被测的实现（经由 Ollama）。`--cache-type-k` / `--cache-type-v`
  就是 `OLLAMA_KV_CACHE_TYPE` 在设的开关，它的分配器是最可能藏着 8192 台阶的地方。
  `q8_0` 之所以是 1.0625 字节/元素（32 个数加一个 fp16 缩放因子），出处在那个代码库里，
  不在这里。
- **PagedAttention / vLLM**（Kwon 等，SOSP 2023）是 KV cache 现在都按**块**来讨论的原因。
  本文故意退回更粗的「每 token 字节」口径，因为那才是单卡上一个人真的会拿去乘上下文长度的数。
- **KIVI**（Liu 等，ICML 2024，arXiv:2402.02750）把 K 按通道量化、V 按 token 量化，报的
  是含权重在内的峰值显存下降。它算的是端到端账单；本文是它的补集——拆解量化之后**仍然剩下**
  的那部分开销。
- **QServe / QoQ**（Lin 等，MLSys 2025，arXiv:2405.04532）在数据中心卡上推到 W4A8KV4，
  报的是吞吐，不是常驻显存。

缺的东西，缺得明白：没有任何一项是在同一块卡上和上面这些做过对照。本文的主张很窄——
在这套配置上，横穿五个上下文点拉一条直线，会把每 token 成本报偏约 7%，而且这个偏差是有形状的。
这个形状在 vLLM、TensorRT-LLM 或数据中心卡上是否还在，没测过，那才是明显的下一步。

## 用法

### 测一组配置

```bash
# q8_0 的 KV cache
python scripts/ollama_probe.py --tag q8_0 --kv-bytes 1.0625

# f16 基准
python scripts/ollama_probe.py --tag f16  --kv-bytes 2
```

输出：逐 `num_ctx` 的表、带 1 SE 与 95% 置信区间的最小二乘拟合、外推表，
以及 `ollama_probe_<tag>.csv`。

常用参数：

| 参数 | 含义 |
|---|---|
| `--kv-bytes` | 每元素字节数：f16=2、q8_0=1.0625、q4_0=0.5625。**它只给这一轮贴标签，不配置 Ollama**——脚本会去读服务端的 `OLLAMA_KV_CACHE_TYPE`，两边对不上就拒绝运行 |
| `--seqs` | 要测的上下文长度（默认 `2048 4096 8192 16384 32768`） |
| `--layers --kv-heads --head-dim` | 模型结构参数，用于理论值那一列 |
| `--samples` | 每个点读几次 `nvidia-smi`，取峰值（默认 7；本仓库的测量用的是 9） |
| `--aba` | 结尾重测第一个上下文，作为基线漂移探针 |
| `--bracket` | 用每次加载前后两个空闲值的均值做基线，抵消单调漂移 |
| `--settle` | 回退卸载判定的显存容差（MiB），只在 `/api/ps` 不可达时使用 |
| `--allow-kv-mismatch` | 明知标签与环境不符仍然继续，并在 CSV 里记为"未校验" |

### 切换真正的 KV 类型

设环境变量**并重启服务**——这个设置只在加载时读取。

```bash
export OLLAMA_FLASH_ATTENTION=1          # V 量化强制要求
export OLLAMA_KV_CACHE_TYPE=q8_0         # 或 f16 / q4_0
ollama serve
```

> Windows：用 `set`（只影响当前窗口，立即生效），不要用 `setx`（只对之后新开的窗口生效）。
> 改完必须重启 `ollama serve`，否则不生效。

### 测量协议

每个 `num_ctx`，按顺序做四步：

1. `ollama stop <model>`，然后轮询 `/api/ps` 直到模型消失。**不要用显存阈值判这件事。**
   绝对阈值分不清"模型还在"和"桌面变大了"，而在这台机器上，十分钟里空闲底线抬了 150 MiB，
   脚本因此报了三次"模型可能没卸载干净"，而 `ollama ps` 全程是空的。
2. 连读五次 `nvidia-smi`，取**中位数**。这就是**空闲值**。单次读数是掷硬币——这台桌面上
   8 秒内峰峰差 32 MiB。
3. 发一个请求按该 `num_ctx` 加载，然后连读九次 `nvidia-smi`，取**峰值**。加载后要峰值不要
   中位数：加载态本身就是那次分配，取中位数会把高档位削掉 300–600 MiB，而看起来完全像是
   "KV 更便宜"。这个错在 v0.2 开发时真犯过，也真被抓到了。
4. **加载后减空闲，就是这次测量。** 再拿 runner 自报的 `size_vram`（`/api/ps`）对一遍：
   两者应相差一个恒定的约 105 MiB 的 CUDA 上下文；如果这个差**不**恒定，说明基线在加载
   过程中动过，这一行就不可信。

**永远比差值，不比绝对值。** 原始测量与它的复现之间，桌面占用差了 1078 MiB，差值把这点
完全吸收了，两次结果吻合到 4 MiB。

**没有**被控制、应当计入误差预算的部分：GPU 频率与功耗状态交给驱动决定；驱动与 CUDA 版本
没写进 CSV；桌面的环境负载只体现在空闲读数里；每一轮里每种配置只加载**一次**。`load_sec`
写进 CSV 只为留痕，不参与分析。

**没有控制住的**，应当计入误差预算：GPU 频率与功耗状态交给驱动自己看着办；驱动版本和
CUDA 版本没写进 CSV；桌面的背景负载只体现在那次空闲读数里；每组配置只加载了**一次**。
`load_sec` 记进 CSV 是留作出处，没有参与分析。

### CSV 字段

| 列 | 含义 |
|---|---|
| `num_ctx` | 请求的上下文长度 |
| `loaded_mib` | 加载后的绝对显存（仅用于排查） |
| `delta_mib` | **测量值** —— 加载后减空闲 |
| `idle_mib` | `delta_mib` 相减时用的那个基线。v0.1.3 才有；两份历史 CSV 早于这一列，用 `loaded_mib − delta_mib` 反推 |
| `theory_kv_mib` | 同一行按教科书公式算出的纯 KV |
| `load_sec` | 加载耗时 |
| `model`、`ollama_version`、`kv_cache_type`、`kv_bytes_per_elem` | 出处信息 |

`delta_mib` 里含权重。这是故意的：拟合的截距会把权重吸收掉，权重就是靠这一手
才跟每 token 成本分开的。

## 这个仓库不是什么

- **不是 benchmark。** 没有 tokens/s、没有延迟、没有质量评测，只有显存。
- **没有重复测量。** 每个 `num_ctx` **只加载一次**。置信区间里那三个自由度全部来自模型
  残差，不含一次纯重复，所以做不了失拟检验，误差棒是偏乐观的。这是这批数据最大的弱点，
  也是路线图第一条。
- **一台机器、一个模型。** 每组配置五个点。方法通用，数字不通用。本机在桌面繁忙时，
  空闲基线差出 **419 MiB**（1230 vs 811）——在 32K 跨度上，这一项就能让两点斜率偏移 14 KiB/token。
- **不是"q8_0 无损"的证据。** 业界共识是近似无损，但本仓库没验证。别拿它当证据。
- **台阶的机制不明。** 上面列了三个候选，一个都没确认。别引用本仓库解释台阶**为什么**
  存在，只能引用它说明在这套配置上台阶**存在**。
- **置信区间很宽。** 自由度只有 3。要更紧的数字，就多测几个点——脚本会诚实报出区间。
- **空闲基线当初没记录。** v0.1.3 之前，CSV 存了 `delta_mib` 和 `loaded_mib`，却没存拿来
  相减的那个空闲读数——q8_0 那轮 26 MiB 的漂移就是这么躲过两个版本的。现在记了。历史 CSV
  故意保持逐字节不变：为了一条一手记录好看而补一列事后重建的字段，比承认这列缺了更糟。

社区测量会汇总成一张表，标上卡型号和斜率。**方法才是重点，数字本来就该不一样。**

借自硬件算子库（如 [FlashMLA](https://github.com/deepseek-ai/FlashMLA)）所在的那个
系统测量传统：**公布数字、公布能复现它的命令、说清它成立的边界。**
